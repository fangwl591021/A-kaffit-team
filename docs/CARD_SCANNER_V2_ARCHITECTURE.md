# A-KAFFIT Card Scanner V2 技術規格

版本：V2.0 Draft  
分支：`agent/card-scanner-v2`  
目標：以低成本、低延遲、低記憶體消耗方式完成名片拍攝、裁切、透視補正、品質檢查與 OCR 前置處理。

---

## 1. 重新架構原因

舊版智慧裁切把「找名片」、「裁切」、「OCR」、「二次驗證」、「CRM 分析」綁得太緊，且自動裁切主要依賴背景顏色與前景差異。在實際外出拍攝情境中，背景可能包含手指、鍵盤、桌面、筆電、貼紙、螢幕、陰影、反光，這會造成錯誤定位。

V2 不再把自動裁切視為 AI 主流程，而是把它定義為「零 token 的本機文件掃描前處理」。AI 只負責最終 OCR 與後續非同步資料分析。

核心原則：

1. 裁切與透視補正不使用生成式 AI。
2. 不完整、模糊、過暗、嚴重反光的照片不送 OCR。
3. 自動定位信心不足時直接進人工裁切，不硬猜。
4. 人工裁切一旦確認，即為最終裁切權威，不再執行自動裁切。
5. OCR 與裁切解耦；OCR 只接受「已完成裁切的最終圖片」。
6. 禁止生成式補圖、猜字、補 Logo、補不存在的名片邊界或聯絡資料。

---

## 2. 使用者實際拍攝情境

V2 必須至少支援以下兩類常見情境：

### 2.1 手持名片

特徵：

- 名片周圍可能有手指、皮膚、電腦螢幕、鍵盤。
- 名片通常略有透視變形。
- 四個角多半完整存在。

預期行為：

- 找到四條主要邊界。
- 排除手指與背景雜訊。
- 計算四個角點。
- 進行透視補正。
- 補正後再進 OCR。

### 2.2 名片放在桌面或筆電上

特徵：

- 背景可能有鍵盤、貼紙、金屬紋理、桌面紋路。
- 名片可能靠近照片邊界。
- 可能出現名片局部超出畫面的情況。

預期行為：

- 若四角完整：自動裁切與透視補正。
- 若任一真實邊界或角點超出照片：判定「未完整入鏡」，要求重拍。
- 不得根據名片標準比例憑空補出缺失區域。

## 3. 整體流程

```text
手機拍照 / 相簿選圖
        ↓
[Stage 0] 影像正規化（0 token）
        ↓
[Stage 1] 分析圖產生（0 token）
        ↓
[Stage 2] 四邊 / 四角偵測（0 token）
        ↓
[Stage 3] 完整性 + 品質檢查（0 token）
        ↓
 ┌──────┼───────────────┐
 │      │               │
重拍   人工裁切        自動裁切
 │      │               │
0 token 0 token          0 token
 │      │               │
 └──────┴───────┬───────┘
                ↓
[Stage 4] 透視補正 / 最終輸出
                ↓
[OCR Gate]
                ↓
只允許合格最終圖片進 OCR
                ↓

                ↓
名片欄位人工校正
                ↓
儲存名片
                ↓
CRM / 五大標籤背景非同步
```

## 4. 解析度策略

手機相機原始照片通常為 12MP、48MP 甚至更高。直接在 LINE LIFF / WebView 中對 4000px 以上圖片做多次 Canvas、旋轉、邊緣偵測、透視補正，會造成：

- 記憶體高峰過大。
- Android WebView 卡頓或白屏。
- Canvas 建立失敗。
- 上傳時間增加。
- OCR 前置處理時間增加。
- 無效 AI 成本提高。

因此 V2 必須使用三層影像尺寸。

### 4.1 原始輸入 Original Input

用途：僅作為使用者選取或拍照來源。

規則：

- 接受 JPEG / PNG / WebP。
- 可接受大尺寸原圖，但不得直接進主分析演算法。
- 原始照片若無稽核需求，不應長期保存。

### 4.2 工作圖 Working Image

用途：

- 自動透視補正的高品質來源。
- 人工裁切來源。
- 最終 OCR 圖輸出的母圖。

規格：

- 長邊最大：2200 px。
- 原圖長邊 <= 2200 px：保持原尺寸。
- 原圖長邊 > 2200 px：等比例縮至長邊 2200 px。
- 建議 WebP / JPEG quality 約 0.86。

### 4.3 分析圖 Analysis Image

用途：

- 邊緣偵測。
- 長直線偵測。
- 四角定位。
- 完整度判斷。
- 模糊、亮度、反光等品質評估。

規格：

- 長邊目標：1280 px。
- 不需要上傳。
- 不需要永久存檔。
- 只存在前端記憶體 / Canvas。

### 4.4 最終 OCR 圖 Final OCR Image

用途：

- 唯一允許送進 OCR 的圖片。
- 收藏名片顯示圖。
- 必要時存入 R2。

建議規格：

橫式名片：

- 1600 × 960 px 為目標尺寸。
- 若來源不足，不強制放大到產生假細節。

直式名片：

- 960 × 1600 px 為目標尺寸。

格式：

- WebP 優先，JPEG 為相容備援。
- quality 約 0.86。
- 目標檔案大小約 250 KB ～ 600 KB，實際以文字可讀性優先。

### 4.5 尺寸流程示例

```text
原圖：4032 × 3024
        ↓
工作圖：2200 × 1650
        ↓
分析圖：1280 × 960
        ↓
找四角（分析圖座標）
        ↓
換算回工作圖座標
        ↓
在工作圖做透視補正
        ↓
最終 OCR 圖：1600 × 960
```

## 5. EXIF 與方向正規化

任何邊緣分析之前都必須先處理圖片方向。

流程：

1. 解碼圖片。
2. 依瀏覽器已套用的 EXIF orientation 或可取得之方向資訊完成轉正。
3. 統一以實際顯示方向建立 Working Image。
4. 所有後續座標均以已轉正圖片為準。

不得讓 EXIF 方向與 Canvas 實際方向不一致，否則四角座標會錯位。

---

## 6. 自動四邊偵測

V2 不再使用「背景顏色差異 = 名片」作為主要判斷。

主要證據改為幾何結構：

1. 灰階化。
2. 降噪。
3. Sobel / Canny 類邊緣訊號。
4. Hough 類長直線候選。
5. 水平 / 垂直或成對近平行線分組。
6. 找出合理的四條外邊界。
7. 計算四個交點。
8. 驗證四邊形凸性、比例、面積與透視程度。

### 6.1 四邊形基本條件

候選四邊形應滿足：

- 4 個角點。
- 凸四邊形。
- 面積不可過小。
- 面積不可接近整張照片到失去邊界意義。
- 長寬比例須符合常見名片合理範圍，但不可用比例硬補不存在的邊。
- 相對邊應具有合理平行關係。
- 四條邊應具有足夠邊緣支撐。

### 6.2 名片比例

一般橫式名片可使用約 1.55 ～ 1.85 的寬高比合理區間作為評分條件，而不是絕對拒絕條件。

原因：

- 不同國家 / 公司名片尺寸不同。
- 可能為直式名片。
- 拍攝透視會改變視覺比例。

比例只提供 confidence，不得成為「自動生成缺邊」的依據。

---

## 7. 完整性檢查

完整性優先於 OCR。

### 7.1 必須重拍的狀況

- 無法確認四角，且候選名片區域明顯碰到照片邊界。
- 左 / 右 / 上 / 下任一真實邊界疑似超出畫面。
- 名片面積太小導致文字解析度不足。
- 嚴重模糊。
- 嚴重過暗。
- 大面積過曝 / 反光遮蔽主要文字。

### 7.2 邊界風險

若候選角點距離圖片邊界低於安全距離，必須降低完整性信心。

例如：

```text
leftEdgeTouchesImageBoundary = true
```

此時不得只因名片比例合理就宣告裁切成功。

### 7.3 UX 提示

建議文案：

- `名片左側未完整入鏡，請稍微拉遠再拍。`
- `名片四個角需要完整出現在畫面內。`
- `照片較模糊，請穩定手機後重新拍攝。`
- `反光遮住部分文字，請稍微改變拍攝角度。`

---

## 8. 品質檢查（全部 0 token）

V2 可用本機統計值評估以下項目：

### 8.1 清晰度

可使用：

- edge strength。
- Laplacian variance 類指標。

目的：擋掉嚴重手震或失焦照片。

### 8.2 亮度

可使用：

- 灰階平均值。
- histogram。
- 暗部像素比例。

### 8.3 過曝 / 反光

可使用：

- 高亮像素比例。
- 大塊連續高亮區域。
- 名片候選區域內的高亮遮蔽比例。

### 8.4 覆蓋率

名片不應太小，也不應大到緊貼畫面四邊。

---

## 9. 信心分流

系統不採二元「成功 / 失敗」，而是三段分流。

### A. 高信心：自動裁切

建議條件：

- 完整性通過。
- 四角可信。
- 邊界支撐充分。
- 品質通過。
- scanner confidence >= 約 0.85（實際門檻須用實拍資料校正）。

行為：

- 自動透視補正。
- 顯示短暫預覽或直接進 OCR。

### B. 中信心：人工確認 / 調整

行為：

- 系統先提供預估裁切框。
- 使用者可以直接確認或拖動四角 / Cropper。
- 確認後立即產生 final image。
- 不再重新跑自動裁切。

### C. 低信心

若圖片完整但幾何定位不可靠：

- 直接進人工裁切。

若圖片本身不完整或品質太差：

- 直接要求重拍。

---

## 10. 人工裁切權威規則

這是 V2 的不可違反規則。

```text
人工裁切
   ↓
使用者確認
   ↓
manualConfirmed = true
   ↓
產生 Final OCR Image
   ↓
直接 OCR
```

禁止：

```text
人工裁切
   ↓
再跑 AI / 自動裁切
   ↓
再判斷一次
```

人工確認代表使用者已取代自動裁切的判斷權。

---

## 11. 透視補正

自動或人工取得四角後，可做四點透視轉換。

輸入：

- TL 左上
- TR 右上
- BR 右下
- BL 左下

輸出：

- 正矩形名片。

補正允許：

- Perspective / Homography。
- 旋轉。
- 白平衡。
- 適度亮度調整。
- 適度對比增強。
- 輕度銳化。

補正禁止：

- 生成不存在的邊界。
- AI inpainting。
- 補文字。
- 補 Logo。
- 猜測聯絡資料。
- 把原本不存在的像素當真實資料。

---

## 12. OCR Gate

OCR Gate 是成本控制核心。

只有以下兩種圖片能進 OCR：

1. 自動掃描成功且通過完整性 / 品質門檻的 final image。
2. 使用者人工裁切並確認的 final image。

以下狀態不得進 OCR：

- `retake_required`
- `incomplete_frame`
- `severe_blur`
- `severe_glare`
- `too_dark`
- `manual_required` 但尚未人工確認

### 12.1 OCR 次數原則

正常流程：

- 每張名片只做 1 次必要 OCR。

人工裁切流程：

- 人工裁切本身不消耗 token。
- 確認後走同一個正常 OCR，不增加額外「裁切 AI」。

### 12.2 OCR 失敗

OCR 失敗時應區分：

- 圖片問題 → 引導重新裁切 / 重拍。
- AI 服務暫時錯誤 → 可重試 OCR。

不得因 OCR 服務錯誤再次跑自動裁切。

---

## 13. OCR 後資料流程

OCR 完成即可建立可編輯名片資料。

優先欄位：

- 姓名。
- 英文名。
- 公司。
- 職稱。
- 部門。
- 手機。
- 公司電話。
- Email。
- 網站。
- LINE。
- 地址。
- 服務內容。

使用者可人工校正。

人工校正資料為主資料，不得被舊 OCR 結果覆蓋。

---

## 14. CRM / 五大標籤解耦

名片建立不得等待：

- 公司公開資料搜尋。
- AI CRM。
- 五大標籤。
- 新聞。
- 社群資料。
- 行業補強。

上述功能全部應背景非同步。

```text
OCR 完成
 ↓
名片立即可用
 ↓
背景排入 CRM / Insights
```


## 16. 前端模組責任

建議模組：

### `card-scanner-v2-resolution.js`

責任：

- decode image。
- orientation normalize。
- working image 2200px。
- analysis image 1280px。
- 座標縮放換算。
- final image 輸出尺寸控制。

### `card-scanner-v2.js`

責任：

- 邊緣分析。
- 長直線偵測。
- 四邊形候選。
- 四角排序。
- confidence。
- completeness。
- quality。
- perspective warp。

### `card-scanner-v2-gate.js`

責任：

- auto / manual / retake 分流。
- OCR eligibility。
- 人工確認權威。
- 錯誤原因與 UI message。

### Cropper

責任：

- manual fallback。
- 使用者確認後直接輸出 final image。

---

## 17. 後端責任

後端不負責名片幾何辨識。

後端主要負責：

- 接收 final image。
- R2 儲存。
- OCR 呼叫。
- OCR 結果寫入 D1。
- 防重。
- 狀態管理。
- 背景 CRM / Insights。

不得要求後端 AI 再判斷「裁切對不對」。

```text

  ↓
scanning
  ├─→ retake_required
  ├─→ manual_required
  └─→ auto_ready

manual_required
  ↓

  ↓

  ↓

  ↓

review_ready
  ↓

  ↓

```

## 19. 禁止的架構回歸

未來任何修改不得重新導入以下模式：

1. 每張照片先送 GPT/Gemini 判斷裁切位置。
2. 自動裁切失敗後仍直接把完整原圖送 OCR。
3. 人工裁切後再跑一次智慧裁切。
4. OCR 與 CRM / 五大標籤綁成同步流程。
5. 利用生成式 AI 補缺失名片區域。
6. 因 AI 驗證結果與人工修改不同而覆蓋人工資料。
7. 直接對 4000px ～ 8000px 原圖執行多次 Canvas 全尺寸分析。

## 20. 測試案例矩陣

至少必須測：

### 拍攝姿勢

- 手持橫式名片。
- 手持直式名片。
- 桌面平放。
- 筆電上平放。
- 30 度左右斜拍。
- 輕微旋轉。

### 背景

- 白桌。
- 木桌。
- 金屬筆電。
- 鍵盤。
- 螢幕。
- 手指遮在名片外側。
- 有貼紙 / Logo 的背景。

### 失敗案例

- 左邊超出照片。
- 右邊超出照片。
- 上下缺角。
- 嚴重反光。
- 模糊。
- 名片太遠。
- 深色名片 + 深色背景。
- 白名片 + 白背景。

### 驗收標準

- 不完整照片不得自動宣告成功。
- 完整且清楚的常見名片應優先自動完成。
- 中信心應能快速人工確認。
- 人工確認後不再觸發自動裁切。
- 重拍流程不得呼叫 OCR。
- final image 解析度符合政策。
- Android LIFF 不得因高解析度照片導致明顯卡死或白屏。

---

## 21. 效能指標

建議目標（需實機驗證後調整）：

- Analysis Image 建立：< 500 ms ～ 1 s。
- 四邊偵測：中階手機盡量 < 1 s。
- 透視補正：< 1 s。
- 自動掃描前處理總時間：目標 1 ～ 2.5 s。
- 不把網路上傳計入本機掃描時間。

若裝置性能不足，可降低 analysis long edge，例如從 1280 降到 960，但 working image 仍保留較高解析度。

---

## 22. 記憶體管理

必須：

- 及時 `URL.revokeObjectURL()`。
- 不同 Canvas 使用完即解除引用。
- 不同階段避免同時保留多份全尺寸 RGBA buffer。
- 只在需要時建立 ImageData。
- 可用 `createImageBitmap()` 時優先使用以降低解碼阻塞。
- Worker / OffscreenCanvas 僅作能力增強，不可成為 LIFF 必要條件。

---

## 23. R2 儲存政策

V2 建議：

### 最省模式

只永久保存：

- final OCR image。

原始大圖與 analysis image 不永久保存。

### Debug / 灰度測試模式

必要時短期保存：

- 原圖。
- scanner metadata。

但應有 TTL / 清除策略，不應永久累積。

```json
  },
  "manualConfirmed": false
}
```

不需要把圖片內容、OCR 全文或 AI prompt 放入 scanner metadata。

## 25. 上線策略

### Phase 1：V2 Shadow

- V2 只計算，不影響正式 OCR。
- 記錄 V2 建議 route / confidence。
- 比較既有流程結果。

### Phase 2：人工確認優先

- 高信心自動預裁。
- 仍顯示確認。
- 收集錯框率。

### Phase 3：高信心自動

- 高信心直接進 final image。
- 中信心人工。
- 低信心重拍 / 人工。

### Phase 4：正式替換舊智慧裁切

前提：

- Android / iOS LIFF 實拍通過。
- OCR 成功率不低於舊流程。
- 無效 OCR 呼叫明顯下降。
- 人工修正率在可接受範圍。

## 26. 最終不變原則

Card Scanner V2 的產品定位不是「用 AI 把任何照片救回來」，而是：

> 用免費、快速、可靠的本機掃描先把能處理的照片整理好；不能可靠處理的，立刻交給使用者或要求重拍；只把真正合格的名片圖片交給 AI OCR。

因此最終架構必須長期遵守：

**本機免費處理 → 人工 fallback → 單次 OCR → 背景 AI 補強。**
